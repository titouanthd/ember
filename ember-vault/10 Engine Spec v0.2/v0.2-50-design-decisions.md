## ADR-050: Frame snapshot on `NodeContext`

**Status:** accepted (2026-11-27) — round V1.1, [[Next Phase Plan — Engine v0.2 & Game 18]]

### Context

Nodes had `delta()` but no clock, no pointer and no viewport of their
own: they dug into `ctx.input().mouse_pos` and `ctx.render().viewport()`
and kept their own elapsed-time counters. accretion and ember-wars each
wrote a thread-local `frame.rs` standing in for macroquad's `get_time` /
`mouse_position` / `screen_width`; asteroids, pagoda, zhuo-ji and others
keep a `time` field fed from `process`. Rule of Three met several times.
Game 18 needs the pointer in world space (tap → grid cell) and a clock
for its animations.

### Decision

- **The clock lives on `NodeTree`**: `NodeTree::time() -> f64`, summed
  from every `process` `dt` at the start of the pass (negative or NaN
  `dt` ignored). No change to `Servers`, `MainLoop` or the runners, and a
  tree driven by hand in a test gets the same clock as one in a
  `SceneLoop`.
- **`NodeContext`** reads the snapshot: `time()`, `frame()`,
  `viewport()`, `camera()`, `pointer()`, `pointer_world()`. Accessors, not
  a stored struct: each reads the tree or a server as it is now, so there
  is nothing to keep in sync.
- **`DrawContext::time()`**, set by `NodeTree::draw`, so draw-time
  animation (pulses, blinks, twinkles) needs no field. `DrawContext::new`
  keeps its signature; a context drawn outside a tree reads `0.0`.
- **`f64`** for time, as macroquad's `get_time`: `f32` loses
  millisecond precision after a few hours.
- **`pointer()`** is the first touch, else the mouse, in viewport
  coordinates (canvas coordinates under ADR-041). **`pointer_world()`**
  maps it through the renderer's current camera (ADR-040), the same
  transform `DrawContext::screen_to_world` uses.

### Alternatives

- *A `FrameInfo` value in `Servers`*, filled by the runner: every
  `Servers { .. }` literal (scene loop, editor, test harnesses) would
  change, and hand-driven trees would see no clock.
- *A world-camera field on the tree* that `SceneLoop` applies when it
  draws: the honest home for "pointer in world space", but it changes how
  every game sets its camera. Left for when a camera node arrives.
- *`f32` time*: matches `delta`, but drifts; rejected.

### Consequences

- `pointer_world()` is only as right as the renderer's camera at the
  time of the call; a game that sets its camera only in `draw` sees last
  frame's camera in `process` (identity under a virtual resolution, which
  `SceneLoop` resets after drawing). Documented on the method.
- Games may drop their `frame.rs` / `time` counters when a round touches
  them; none is migrated in V1.1.
- V1.1 also removes `Cooldown::new` / `with_duration`, deprecated in
  0.1.0 (ADR-011), as [[02-principles]] asks.

## ADR-051: Typed tree queries and node groups

**Status:** accepted (2026-11-28) — round V1.2, [[Next Phase Plan — Engine v0.2 & Game 18]]

### Context

[[21-ember-scene]] §5.2 listed `find_by_class` / `find_all_by_class` as
"not yet implemented", and [[42-acceptance-tests]] §5.4 falls back to
walking `children(units_id)` by hand ([[Doc–Code Discrepancies]] #14).
The workspace has ~90 `tree.get(id)?.as_any().downcast_ref::<T>()`
chains, and the "children of class `T`" helper was written again in M3.
Game 18 needs "every lantern", "every pushable piece" — a set that cuts
across the tree, which is what Godot's groups are for. [[30-escene-format]]
Q1 deferred groups to v0.2; the user chose to add them now (2026-11-28,
plan open question 3) rather than wait for a third user.

### Decision

- **The class is the Rust type.** Queries are generic, `T: Node`, and
  match by downcast through `Object::as_any` — no `ClassDB` needed, no
  string to mistype, and the result is already typed.
  - `NodeTree::get_as::<T>(id)` / `get_as_mut::<T>(id)`.
  - `find_by_class::<T>(from) -> Option<NodeId>` and
    `find_all_by_class::<T>(from) -> Vec<NodeId>`: descendants of `from`,
    **not** `from` itself, in `descendants` order (depth-first, top-down,
    child order — the `process` order).
  - `children_of::<T>(id) -> impl Iterator<Item = (NodeId, &T)>`: direct
    children only, child order.
  - On `NodeContext`: `find_by_class::<T>()` / `find_all_by_class::<T>()`
    search the **whole tree** from the root (root included);
    `children_of::<T>()` reads the current node's children. The current
    node is checked out during its callback, so it is never found.
- **Groups are a tree-side index**, not a node field: the derive and
  the `Node` trait are unchanged, and any node — hand-written or
  derived — can be grouped.
  - `add_to_group(id, &str) -> bool`, `remove_from_group`, `is_in_group`,
    `nodes_in_group(&str) -> Vec<NodeId>`, `groups_of(id) -> &[String]`,
    `group_names()` (sorted). `bool` returns as `HashSet::insert`: `false`
    for a repeat, an empty name, or a stale id.
  - **Order:** members in **join order**; rejoining goes to the back.
    A node's own groups also in join order. Deterministic, and it lets a
    load → save round trip keep the file's text.
  - A node queued by `spawn` may join at once (so a node can tag what it
    spawns); it is listed only once flushed in. `remove` / `despawn` /
    `clear` take removed nodes out of every group; a group left empty
    disappears.
  - `NodeContext`: `add_to_group`, `remove_from_group`, `is_in_group`
    (current node), `nodes_in_group`.
- **`.escene`:** an optional `groups: ["a", "b"]` list per node entry,
  joined in order at instantiation. Absent means none, and `SceneWriter`
  writes no key for an empty list, so v0.1 files load and save byte for
  byte as before; `format` stays `1`. Empty or repeated names are a
  parse error. On an `instance:` entry the listed groups are added after
  the nested root's own. `from_tree` / `resave` write each node's
  current groups. `NodeRecord` gains `groups: Vec<String>`.

### Alternatives

- *String class names* (`find_by_class("Unit")`), as Godot: needs a
  `ClassDB` at the call site and returns an untyped id; the generic form
  covers every use in the repo. A `ClassDB`-based form can be added if
  the editor needs one.
- *`find_by_class` including `from`*: `ctx`'s whole-tree form does
  include the root; the tree form follows `descendants`, which excludes
  `from`, so the two never disagree about a subtree.
- *Groups stored on the node* (a derive field or a `Node::groups()`
  method): every node type would carry it, and hand-written nodes would
  have to implement it.
- *Groups sorted by tree order*: needs a walk per query and changes as
  nodes move; join order is cheap and stable.
- *Bumping `format` to 2*: the field is additive and defaulted, so a v0.1
  loader simply ignores it.
- *`@Group` in `find` paths* ([[21-ember-scene]] §5.6): not needed yet.

### Consequences

- Most hand-written `as_any().downcast_ref` chains can become `get_as`;
  none is migrated in V1.2.
- `NodeRecord` literals must set `groups` (one in the workspace, a test).
- A v0.1 engine reading a v0.2 file with groups drops them silently (no
  `deny_unknown_fields`); there is no v0.1 user left to care.
- `nodes_in_group` filters stale and queued ids on every call: O(members).

## ADR-052: Input action map

**Status:** accepted (2026-11-28) — round V1.3, [[Next Phase Plan — Engine v0.2 & Game 18]]

### Context

[[15-input]] §2.2 and §5–6 designed named actions loaded from RON
(`action`, `action_pressed`, `action_axis`) but nothing existed
([[Doc–Code Discrepancies]] #13). Every game hard-codes `Key::A ||
Key::Left` pairs. Game 18 needs one "move left" from arrows, WASD, the
d-pad **and a swipe**, so the same code runs on desktop, web and phones.
Gamepads have digital buttons only (no sticks: the backend reports none),
and touch gives raw points with no gestures.

### Decision

- **Data and state are split.** `ActionMap` (in `ember-input`) is the
  bindings: serde + RON, `from_ron` / `to_ron` / `validate`, and a
  builder (`with_key`, `with_gamepad`, `with_mouse`, `with_swipe`).
  `ActionResolver` owns a map plus what it remembers across frames.
  `resolve(&mut Input)` writes the frame's result into a new
  **`Input::actions: ActionState`** field.
- **Queries stay on `Input`**, so a node writes
  `ctx.input().action_pressed("move_left")`, as spec 15 drew it:
  `action` (down), `action_pressed`, `action_released`, `swipe()`.
  An unknown name is `false`. With no resolver every query is idle.
  `Input` stays a plain `Default + Clone` fixture (ADR-018).
- **`SceneLoop::with_action_map(map)`** / `set_action_map(Option<_>)` /
  `action_map()` run a resolver in `set_input`, after the
  virtual-resolution mapping (ADR-041), so swipe distances are in canvas
  units. Swapping the map is the runtime rebinding of spec 15 §11 Q3; it
  resets held state.
- **Edges come from the resolver, not from the raw lists.** An action
  is down while any binding is down (or pressed this frame); pressed and
  released are edges of that across frames. So holding `A` and then
  pressing `Left` presses `move_left` once (spec 15 §5.2), and a key may
  serve several actions (§5.3). Result lists are in map order.
- **Bindings:** `keys`, `gamepad` (buttons), `mouse` (buttons) and
  `swipe` (`Left` / `Right` / `Up` / `Down`). A swipe is recognised
  **once per stroke**, on the first frame the finger is
  `swipe_distance` (default 32) away from where it touched down, in the
  dominant direction (a tie goes to the horizontal); a quick flick is
  caught on its `Ended` frame. A swipe-bound action is down for that one
  frame. `mouse_swipe: true` reads a left-button drag the same way
  (off by default, since it would turn every drag into a swipe).
- **Axes are two actions**, as Godot's `get_axis`:
  `action_axis(negative, positive) -> f32` is `-1`, `0` or `+1`;
  `action_vector(left, right, up, down)` scales a diagonal to length 1.
- **RON format** (`input.ron`):
  `(swipe_distance: 32.0, mouse_swipe: false, actions: [(name, keys,
  gamepad, mouse, swipe)])`, every list optional. Defaults are left out
  when written. Names are non-empty and unique (`ActionMapError`).

### Alternatives

- *The map inside `Input`*: `Input` is rebuilt every frame by the
  backend, and edges and swipes need memory across frames.
- *`ActionMap::pressed(&input, "jump")` queries*: no state for edges or
  swipes, and every node would need the map.
- *A one-name `action_axis("move_left")` with dead zones* (spec 15 §6):
  no analog source exists yet. Dead zones and stick bindings come with
  real gamepad axes; the format can add `dead_zone` without breaking.
- *Swipe on lift only*: feels late on a phone; firing at the distance
  is what puzzle games do.
- *An `Asset` impl for hot reload* (spec 15 §5.4): `ember-input` may not
  depend on `ember-assets` (layers), and the orphan rule rules out an
  impl in `ember-scene`. A game loads with `include_str!` + `from_ron`;
  a reload is `set_action_map`.

### Consequences

- `Input` has one more field; literals using `..Default::default()`
  (every one in the workspace) are unaffected.
- `Key`, `GamepadButton` and `MouseButton` derive `Serialize` /
  `Deserialize`; `ember-input` now depends on `serde` and `ron`.
- A touch that starts a swipe also starts a touch, so it still triggers
  `primary_action` (ADR-010) on its first frame. A swipe-driven game reads
  actions, not `primary_action`, during play.
- No game moved to actions yet; Game 18 (G2) is the first user.
